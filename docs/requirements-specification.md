- **文書種別**: 要求仕様書（基本設計・詳細設計の上位文書）

---

## 2. プロジェクト概要
本プロジェクトは、**完全オフライン**・**サーバーレス**で動作するタスク管理・チャット統合ツールを、VS Code 拡張機能として実装することを目的とする。  
外部ネットワークに依存せず、共有フォルダ上の SQLite データベースを介して、チームメンバーおよびローカル AI エージェントと連携する。

### 2.1 背景
- ローカル開発環境で機密情報を扱う現場では、クラウド型チャット・タスク管理の利用が制限される。
- 既存のローカル運用では、チャット・タスク・AI活用が分断され、情報集約コストが高い。

### 2.2 目的
- VS Code 上でチャットとタスク管理を一体化し、コンテキストスイッチを削減する。
- チーム内情報連携をローカルネットワークまたは共有フォルダだけで完結させる。
- ローカル LLM を活用し、タスク生成・要約などの作業を支援する。

### 2.3 スコープ
**本要求仕様の対象範囲（In Scope）**
- VS Code 拡張機能本体（UI、データアクセス、監視機能）
- 共有フォルダ上 SQLite を利用したチャット・タスク連携
- ローカル LLM 連携（Ollama / llama.cpp 等）

**対象外（Out of Scope）**
- クラウドサーバー構築
- インターネット経由の認証・通知機能
- モバイルアプリ提供

## 3. システムアーキテクチャ要求

### 3.1 技術スタック
- **プラットフォーム**: VS Code Extension（TypeScript）
- **UI レイヤー**: Webview API（React または Vanilla JS/HTML/CSS）
- **データ層**: 共有フォルダ上の SQLite
- **リアルタイム検知**: `vscode.RelativePattern` + `FileSystemWatcher`
- **AI 連携先**: Local LLM（Ollama、llama.cpp 等）

### 3.2 構成要素
1. **Extension Host 層**
   - コマンド受理、DBアクセス、監視イベント処理、LLM呼び出し仲介
2. **Webview UI 層**
   - チャット表示、入力、タスク参照、検索操作
3. **Shared Storage 層**
   - SQLite DB ファイル、添付ファイル格納領域
4. **Local AI Adapter 層**
   - ローカル LLM API とのインタフェース

### 3.3 設計への引き継ぎ方針（基本設計・詳細設計向け）
- 基本設計では、上記構成要素ごとの責務境界と I/F を明確化すること。
- 詳細設計では、テーブル定義、イベントフロー、排他制御、エラー処理を具体化すること。

## 4. 機能要求

## 4.1 チャット機能（Chat Engine）

| ID | 機能名 | 要求内容 | 優先度 |
|:---|:---|:---|:---|
| C-01 | メッセージ送受信 | 共有DBへの書込みと、他者更新の自動反映を行う。 | 高 |
| C-02 | メンション機能 | `@AI` および特定メンバー宛てメンションを認識し、通知・処理振り分けを行う。 | 高 |
| C-03 | ファイル共有 | 共有フォルダへファイルコピーし、相対パスリンクとしてチャット投稿できる。 | 中 |
| C-04 | 履歴検索 | チャット履歴を SQL ベースで高速検索できる。 | 中 |

### 4.1.1 受け入れ条件（例）
- C-01: 送信後、ローカル UI へ即時表示され、他端末更新が監視経由で反映されること。
- C-02: `@AI` を含む投稿が AI 処理キューへ連携されること。

## 4.2 タスク連携機能（Task Integration）

| ID | 機能名 | 要求内容 | 優先度 |
|:---|:---|:---|:---|
| T-01 | タスクID参照 | `#T-123` 形式の記述から対象タスク詳細へジャンプできる。 | 高 |
| T-02 | チャット内タスク生成 | チャット入力からタスクテーブルへ直接 INSERT できる。 | 高 |
| T-03 | ステータス同期 | タスク更新時にチャットへ自動通知（例: 完了）を投稿できる。 | 中 |

### 4.2.1 受け入れ条件（例）
- T-01: 正規表現で ID を抽出し、該当レコード表示に遷移可能であること。
- T-03: `status=done` 更新時、system 種別メッセージが自動生成されること。

## 4.3 AIエージェント機能（AI Agent）

| ID | 機能名 | 要求内容 | 優先度 |
|:---|:---|:---|:---|
| A-01 | 自動タスク化 | `@AI` 依頼文からタイトル・期限を推論し、タスク登録候補を生成する。 | 高 |
| A-02 | コンテキスト把握 | 現在開いているファイル情報をプロンプトへ注入する。 | 中 |
| A-03 | 要約・整理 | チャット履歴を要約し、進捗管理に活用できる形式で出力する。 | 低 |

### 4.3.1 受け入れ条件（例）
- A-01: 推論結果（タイトル・期限・根拠）をユーザー確認後に登録できること。
- A-02: アクティブエディタ情報の未取得時はフォールバック動作があること。

## 5. データ要求（論理モデル）

## 5.1 Chat テーブル
- `id`: INTEGER（PK）
- `sender_id`: TEXT（PC名またはユーザー名）
- `content`: TEXT（本文）
- `type`: TEXT（`user` / `ai` / `system`）
- `related_task_id`: INTEGER（FK, Task.id）
- `timestamp`: DATETIME

## 5.2 Task テーブル
- `id`: INTEGER（PK）
- `title`: TEXT
- `description`: TEXT
- `status`: TEXT（`todo` / `doing` / `done`）
- `priority`: INTEGER
- `created_at`: DATETIME

## 5.3 データ整合性要求
- `related_task_id` は存在する Task レコードを参照すること。
- `status` および `type` は定義済み列挙値のみ許容すること。
- 時刻はソート・比較可能な統一形式で保存すること（実装時に UTC 基準を推奨）。

## 6. 非機能要求

## 6.1 性能
- 通常利用（同時接続 20 名程度想定）で、チャット表示・投稿が実用的な応答速度を維持すること。
- 履歴検索は実用上の待ち時間内で完了すること（詳細指標は基本設計で定義）。

## 6.2 可用性・信頼性
- SQLite の WAL モードを前提に、書き込み競合時の再試行または待機戦略を備えること。
- 監視イベント取りこぼしに備え、定期再読込または整合性チェック手段を設けること。

## 6.3 保守性
- 機能別モジュール分割（チャット、タスク、AI連携、DBアクセス）を行うこと。
- ログレベル（info/warn/error）を定義し、障害解析可能なログを残すこと。

## 6.4 セキュリティ
- 外部ネットワーク非依存を維持すること。
- 機密情報を平文で不用意にログ出力しないこと。

---

## 7. 制約事項・課題
1. **同時書き込み競合**
   - SQLite + WAL でも多人数（20名超）時にロック競合が発生しうる。
2. **共有フォルダパス差異**
   - OS/マウント差異により、絶対パス不一致が生じる。
3. **I/O 遅延**
   - NAS やネットワーク共有の応答遅延により UI 反映が遅れる可能性がある。

### 7.1 対応方針（要求レベル）
- パス管理は相対パス基準を第一とする。
- リトライ・バックオフ・キャッシュ導入可否を設計フェーズで評価する。

## 8. 外部インタフェース要求

## 8.1 ユーザーインタフェース
- VS Code サイドバーまたはパネルからチャット/タスクを操作可能であること。
- 主要操作（送信、検索、タスク作成）がキーボード中心でも実行可能であること。

## 8.2 ローカルAIインタフェース
- ローカル LLM エンドポイントへリクエストし、応答をチャットへ反映できること。
- 接続不可時のユーザー通知・再試行導線を提供すること。
